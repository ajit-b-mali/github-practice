now I am doing deploy.yml

```

name: Deploy to VPS

on:
  push:
    branches:
      - main
  workflow_dispatch:

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      - name: Configure SSH
        run: |
          mkdir -p ~/.ssh
          chmod 700 ~/.ssh

          printf '%s\n' "${{ secrets.VPS_SSH_KEY }}" > ~/.ssh/deploy_key
          printf '%s\n' "${{ secrets.VPS_KNOWN_HOSTS }}" > ~/.ssh/known_hosts

          chmod 600 ~/.ssh/deploy_key
          chmod 600 ~/.ssh/known_hosts

      - name: Deploy to VPS
        env:
          VPS_HOST: ${{ secrets.VPS_HOST }}
          VPS_PORT: ${{ secrets.VPS_PORT }}
          VPS_USER: ${{ secrets.VPS_USER }}
        run: |
          ssh -i ~/.ssh/deploy_key \
            -p "$VPS_PORT" \
            -o IdentitiesOnly=yes \
            -o StrictHostKeyChecking=yes \
            "$VPS_USER@$VPS_HOST" \
            'cd /opt/apps/github-practice && git pull --ff-only origin main && sudo /usr/bin/systemctl restart github-practice && sudo /usr/bin/systemctl is-active github-practice'
```

this workflow does following things

1. runs whenever I push to main
2. prepares ssh credentials on GitHub runner
3. connects to vps as deploy
4. pulls the latest code from GitHub
5. restarts Node.js systemd service
6. checks that the service is active

the flow of nginx is this

```
1. Create a configuration file in /etc/nginx/sites-available/.
2. Define the server block:
	- listen — port and IP address to listen on (usually port 80 for HTTP).
	- server_name — domain name(s) this block handles.
	- root — website's document root (file location).
	- index — default file to serve.
	- location — rules for handling URL paths, such as static files or API proxying.
3. Create a symbolic link in /etc/nginx/sites-enabled/ using ln -s path destination.
4. Test the configuration using nginx -t.
5. Reload Nginx using systemctl reload nginx.
```

2. Complete the entire task.
3. Test your changes locally.
4. Commit your changes.
5. Push the branch to GitHub.
6. Open a Pull Request (it is immediately ready for review).
7. Review your changes.
8. Merge the PR into main.
9. Delete the feature branch.

| Topic               | Why it matters                                               | Priority      |
| ------------------- | ------------------------------------------------------------ | ------------- |

| Git tags & releases | Mark stable versions such as `v1.0.0`                        | Useful        |
| Git stash           | Temporarily save uncommitted changes when switching branches | Useful        |
| Git cherry-pick     | Bring a specific commit from one branch into another         | Later         |
| Git revert          | Safely undo a commit that has already been pushed            | Essential     |
| GitHub Secrets      | Store deployment credentials securely for Actions            | Essential     |
| GitHub Releases     | Publish versioned releases of your project                   | Useful        |
| CODEOWNERS          | Automatically request reviews from specific contributors     | Team projects |

**My recommendation:** Before moving on, make sure you understand these three:

1. `.gitignore`
